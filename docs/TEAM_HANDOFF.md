### D02: 키를 넣기 전에 고칠 코드

아래는 `2a58fe2`의 정적 코드 대조 결과다. 실제 외부 API 호출 재현 결과와 구별한다.

1. `backend/app/adapters/legacy.py`의 관측 호출은 `KMAObsCollector(api_key=...)`지만
   `API/kma_collector.py` 생성자 인자는 `apihub_key`다. 호출/인터페이스를 일치시킨다.
2. 예보 어댑터는 `fetch_forecast(..., nx=..., ny=...)`로 호출하지만 기존 함수는 `region_code`를 받는다.
   발전소 격자를 직접 받도록 계약을 확장하고 기존 호출부와 함께 검증한다. 시도 대표 격자로 되돌려 해결하지 않는다.
3. 예보 함수는 DataFrame을 반환하지만 어댑터는 원시 dict 목록처럼 순회한다.
   반환 컬럼(`timestamp`, `category`, `fcstValue`, `base_date`, `base_time`)과 변환 형식을 합의한다.
   단순히 순회 방식만 바꾸면 `fcstDate`/`fcstTime`이 반환 컬럼에 없어 누락될 수 있다.
4. `KOEN_PLANT_MASTER`의 용량·좌표·격자를 원천과 대조한다. 미등록 ID에 적용하는
   기본 용량 1,000kW·지역·그룹을 실제 메타데이터로 사용하지 말고 미검증 자원으로 격리한다.
5. 발전량/기상에 `available_at=대상시각+1시간`, SMP에 `available_at=대상시각`을
   지정한 현재 코드는 당시 입수 가능성을 입증하지 못한다. 실제 수집시각·발표시각을 보존하고
   과거 가용 시각을 모르는 데이터는 cutoff 검증 피처로 사용하지 않는다.
6. 관측 기상은 현재 `region:<code>` 단위다. 여러 관측소로 확장할 때 관측소 ID가 키에 포함되도록
   바꾸고 발전소-관측소 연결을 별도로 둔다. 같은 지역의 서로 다른 관측값이 충돌하지 않게 한다.
7. 현재 `collect`는 발전량·SMP·기상을 한 번에 수행한다. 기상 오류가 전체 작업/저장을 막을 수 있다.
   원천별 실패 격리와 부분 성공 기록을 설계한다. 빈 응답 0건을 수집 완료 근거로 사용하지 않는다.
8. 발전소 DB 등록은 live 수집 반환 후에만 실행되며 기존 메타데이터 변경은 자동 갱신하지 않는다.
   원천 장애와 독립된 자원 등록/검증 절차, 용량·소속 변경 이력을 구현한다.
9. 저장은 `(source, record_key)` 충돌 시 무시한다. 수정된 실측·SMP를 재조회해도 자동 교체되지 않는다.
   원본과 개정 이력을 보존하는 revision 정책을 정하고 변경 후 정산 재계산을 검증한다.

### D05/D07: 현재 예약과 제안 구분

| 작업 | 현재 코드의 일정 (KST) | 후속 작업 |
|---|---|---|
| 발전량·관측·SMP 통합 `collect` | 매시 :15, 기본 최근 2일 재조회 | 원천 갱신에 맞춘 분리·쿼터·중단 시 checkpoint 복구 |
| 기상 단기예보 `forecast` | 02:20·05:20·08:20·11:20·14:20·17:20·20:20·23:20 | 미제공 재시도, 누락 발표분 catch-up, 격자 요청 공유 |
| 추론 `predict` | 매시 :30 | 모델·피처 연결 후 실제 완료 검증 |
| 정산 `settle` | 예약 추론이 completed일 때 이어 실행 | 실측·가격 입수 후 사후 정산/수정정산 재실행 경로 추가 |
| 재학습 `retrain` | 매월 1일 03:00 | 학습 코드·시간순 검증·후보 등록 연결 |

[SMP 공식 명세](https://www.data.go.kr/data/15131225/openapi.do)는 하루 한 번 23시경 갱신,
1시간 거래 구간의 **끝점** 표기라고 설명한다. 23:20 확인 후 미제공 재시도는 **제안**이며
현재 별도 SMP 예약은 아니다. 발전량 구간과 SMP 구간을 일치시켜야 한다.
기본 2일 lookback이나 APScheduler의 coalesce만으로 장기간 중단한 수집이 복구되지는 않는다.

## 5. VPP와 정산 구현 기준

자세한 식·예외·검증 항목은 [정산 구현 명세](SETTLEMENT_RULES.md)를 먼저 읽는다.

현재 메타데이터 합계는 SOUTH 29.625MW(11개), CENTRAL 22.3333MW(11개),
GOHEUNG 63MW(1개)다. 앞의 두 그룹은 등록값 기준으로 20MW를 초과하지만
소속 자원 적격성·실제 용량·중개계약·등록시험을 검증한 것은 아니다.
63MW 한 자원을 임의 분할해 여러 소규모 자원으로 세지 않는다.
`20MW`가 들어간 그룹명과 목표 용량 필드는 규제 조건 검증을 대신하지 않는다.
현재 구성원 시작일을 2022년으로 일괄 등록하는 코드도 실제 가동/구성 이력으로 간주하지 않는다.

웹에는 SMP 기준 판매금액 추정·예측제도 인센티브·미획득 인센티브를 구분한다.
공개 API 실측과 공식 정산용 전력거래량의 차이를 확인하기 전에는 실제 지급액으로 표시하지 않는다.
현재 모델·학습·정산 클래스는 미설정이며 월별 일정만 있다고 학습 완료가 되는 것은 아니다.

## 7. 실행·증거 남기기

아래는 **기존에 존재하는 명령**이다. 실제 키나 인증 URL을 출력·커밋하지 않는다.
2026-11-19 이 PC는 Docker Linux 엔진 연결 실패 상태여서 이번 인계에서 컨테이너 검증은 하지 않았다.
로컬 `.env` 및 호스트 프로세스의 두 API 키는 미설정이다. 다른 팀원의 비공개 설정은 알 수 없다.

```bash
# 저장소 루트. 기존 .env는 보존한다.
python scripts/init_env.py
docker version
docker compose version
docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 180
docker compose ps -a
```

Docker가 없는 개발 경로는 [별도 안내](DEVELOPMENT_WITHOUT_DOCKER.md)를 사용한다.
코드 결함을 수정하고 서비스별 활용 승인을 받은 뒤, 각자 `.env`에 키와 `PIPELINE_MODE=live`를 설정한다.
`docker compose up -d --build`로 소스 변경과 환경을 적용한다. 그 전에는 disabled를 유지한다.

```bash
docker compose exec worker python -m backend.app.cli run collect
docker compose exec worker python -m backend.app.cli run forecast
docker compose logs --tail 100 worker
docker compose --profile test build tests
docker compose run --rm tests python -m ruff check backend scripts
docker compose run --rm tests
docker compose run --rm migrate alembic -c backend/alembic.ini check
python scripts/smoke.py
```

실제 호출 검증은 `completed` 문자열만 확인하지 말고 원천별 새 행 수·대상시각·최신 갱신·DB 조회를 대조한다.
`skipped`도 CLI 종료 코드 0일 수 있다. 키가 포함된 원시 예외/URL을 남기는 기존 로거도 점검한다.
CSV 적재 CLI는 아직 없으므로 존재하지 않는 import 명령으로 실행했다고 기록하지 않는다.
기존 원본·모델을 덮어쓰거나 DB 볼륨을 삭제하지 않는다.

후속 PR마다 이 문서의 작업 ID, 수정 위치, 키를 제거한 응답 형상, 수집 이력/행 수,
품질 보고, 테스트 결과와 미검증 범위를 기록한다. 모델은 데이터 스냅샷·피처·검증 기간·버전을 함께 남긴다.
이전 54개 테스트 통과 기록은 [기반 구조 검증](VALIDATION.md)의 과거 결과이며
새 live 수집 코드의 실제 응답 검증을 대신하지 않는다.
