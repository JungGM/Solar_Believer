# 기상청 단기예보 자동수집

2026-11-22 운영 설정: **학습용 과거 예보부터 수집**한다.
`--forecast-only --history-first --start 2026-06-01`로 2026-06-01부터
날짜순으로 과거 구간을 먼저 확보하고 최신 날짜까지 이어간다.
날짜가 바뀌면 목표 범위도 계속 확장하며, 처리할 과거 요청을 최신 발표보다 먼저 선택한다.
기존 08시 발표·다음 날 06~21시·14변수와 원본·기존 큐를 보존한다.
기상청 회귀 테스트 11개, 변경 Python 파일 Ruff, `git diff --check` 통과.
아래 2022년 역사 수집 수치와 최신 발표 우선 설명은 이전 기록이다.

2026-11-22 기준. 사용자가 선택한 현재 운영 범위는 **단기예보만**이며 지상관측 수집은 중지했다.
기존 발전량 수집기는 별도 프로세스로 계속 실행한다.

## 범위와 실행

- 예측 대상일 2022-01-01~2026-10-31, 매일 전날 08시 KST 발표분, 대상일 **06~21시 KST**.
- 사용자 지정 고정 정책: 구간 시작 기준 **00~05시 및 22~23시 실측·예측은 0 처리**. 수집기 시간 매핑 기준으로 적용하며 원본은 보존한다. 이 정책은 실제 야간 발전 여부에 대한 판정이 아니다.
- 이미 존재하는 야간 예보 원본은 보존하고 미수집·재시도 큐에서는 해당 시간을 제외한다. 기상 변수 자체를 0으로 조작하지 않는다.
- `hourly_model_records.csv.gz`의 `value_for_model`에 0 처리한 발전량을 저장하며 `value_raw`·처리 여부·정책 버전을 함께 남긴다. 낮 시간의 결측은 그대로 유지한다.
- TMP, TMX, TMN, UUU, VVV, VEC, WSD, SKY, PTY, POP, PCP, SNO, REH, WAV 전체 14변수.
- 첫 대상일은 2021-12-31 08시 발표분을 사용한다. 발표/대상 시각과 변수별 원본을 따로 보존한다.
- 전국 격자 응답은 gzip 원본·SHA-256·키를 제외한 요청 메타데이터로 저장한다. 발전기 좌표와 격자 순서의 연결은 아직 검증하지 않았다.
- 빈 자료·전부 결측인 응답을 발전량이나 기상값 0으로 채우지 않는다. 오류는 재시도한다.
- 최신 예보를 우선 확보하고, 2022년부터 과거 큐를 순서대로 처리한다. 과거 요청 종료일 이후의 공백도 채운다.
- 로컬 `.env`의 `KMA_APIHUB_KEY`를 사용한다. 키는 코드·명령행 인자·메타데이터에 넣지 않는다.

```powershell
# 숨김 백그라운드 실행, 중복 실행 방지
.\scripts\start_kma_collector.ps1
# 발전량 수집과 기상청 수집 함께 시작/중지
.\scripts\start_collector.ps1
.\scripts\stop_collector.ps1
# 직접 실행 (이전에 생성된 STOP 파일이 없어야 함)
.venv\Scripts\python.exe api.py --kma-hub --forecast-only
```

Docker: `docker compose --profile collector up -d collector kma-collector`.
네이티브 백그라운드 수집은 PC가 깨어 있는 동안만 진행한다. 재부팅 뒤에는 시작 스크립트를 다시 실행해야 한다.
`--forecast-only`를 생략하면 관측도 수집하므로 현재 운영에서는 이 옵션을 유지한다.
기존에 받은 관측자료는 보존하고 새 관측 요청만 중지한다.

## 진행 상태와 기간 추정

- `data/kma_hub/collector_status.json`: 활성 소스, 과거 범위, 성공/재시도/빈 응답 수, 최신 작업, 일일 사용량.
- `data/kma_hub/checkpoint.sqlite`: 이어받기 큐·호출 장부. 예전 관측 큐가 남아 있어도 forecast-only 모드에서는 실행하지 않는다.
- `data/kma_hub/raw/`: 원본과 메타데이터. `data/`와 `.env`는 Git 제외 대상이다.
- 과거 큐는 7일 단위로 생성하므로 현재 큐의 건수와 전체 요청 계획량은 다르다.
- 하루 18,000건·4.8GB를 기본 로컬 한도로 사용하며 KST 날짜가 바뀌면 이어받는다.
- 다른 프로세스가 같은 키로 호출한 양은 이 장부에 합산되지 않으므로 별도 대량 작업을 중복 실행하지 않는다.

365일 × 16시간 × 14변수 = **81,760 요청**. 실제 측정한 격자 응답 341,297바이트를 적용하면 약 **27.9GB**다.
4.8GB/일로 최소 약 6일, 최신 수집·오류 재시도·PC 가동시간을 고려해 **약 7~10일**을 예상한다.
현재까지의 짧은 시험 결과를 바탕으로 한 추정이며 완료 기한 보장은 아니다.

## 다른 과거 예보 확보 경로 조사

1. [기상자료개방포털 단기예보 파일셋](https://data.kma.go.kr/data/rmt/rmtList.do?code=420&pgmNo=572): 공식 페이지는 2010년 6월~조회일 전일의 기간별 파일셋을 안내한다. 조회 시각은 UTC다. 파일에 여러 발표·변수가 묶여 있다면 API 요청 수를 줄일 여지가 있다. 로그인 후 실제 파일 구조·권한·속도는 아직 검증하지 않았다.
2. [API Hub 대용량 신청](https://apihub.kma.go.kr/notice.do?seqNotice=23): 장기간 과거·격자자료 수집을 위한 최대 30일 임시 한도 상향. 활용계획서 제출·검토가 필요하고 공지상 검토가 최대 2~3주 걸릴 수 있다. 신청 이메일은 보내지 않았다.
3. [NOAA GFS 공개 아카이브](https://registry.opendata.aws/noaa-gfs-bdp-pds/): AWS 계정 없이 공개 S3 접근 가능. 2022-01-01 및 2026-01-01 00 UTC 실행의 +24h GRIB 인덱스를 실제 조회하여 HTTP 200, 2m 기온과 DSWRF(하향 단파복사) 항목을 확인했다. 전기간 연속성·GRIB 본문·한국 추출 속도는 미검증. 기상청 예보와 해상도·생산체계가 다르다. 초기화 시각과 실제 배포 시각도 구분해야 한다.
4. [Open-Meteo Historical Forecast](https://open-meteo.com/en/docs/historical-forecast-api)는 여러 실행의 초기 구간을 연결한 시계열이므로 전날 특정 시각에 입수 가능한 다음 날 예보로 무조건 취급하면 안 된다. [Previous Runs](https://open-meteo.com/en/docs/previous-runs-api)는 고정 lead-time 자료이나 모델·변수별 기간이 다르다. [Single Runs](https://open-meteo.com/en/docs/single-runs-api)는 문서상 ECMWF IFS HRES가 2024년 3월부터, 다른 모델은 대체로 2026-04-02부터여서 2022~2026 전체를 직접 대체하지 못한다.

대안 자료는 조사·소규모 확인 단계이며 학습자료에 합병하지 않았다. 실제 발전량을 정답으로 두고 당시 입수 가능한 예보만 입력으로 연결해야 한다.
